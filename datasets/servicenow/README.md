# Synthetic ServiceNow data for Splunk ES demos

This directory contains deterministic, synthetic ServiceNow-style data for a
Splunk Enterprise Security demo environment. It is designed to look operationally
realistic without requiring access to a live ServiceNow instance.

The generated rows include both raw ServiceNow-style fields and Splunk
CIM-friendly normalized fields so the events can participate in Splunk ES demo
searches, eventtypes, tags, and data model pivots.

All people, systems, emails, IP addresses, and records are fake. Email addresses
use the reserved `.example` domain, and IP addresses are RFC1918 private ranges.

## CIM normalization

The JSONL and CSV records include normalized fields in addition to raw
ServiceNow-style fields. Important examples:

- Common: `vendor`, `product`, `vendor_product`, `dvc`, `instance`,
  `cim_data_model`, `cim_dataset`, `tag`
- Change model: `action`, `change_type`, `object`, `object_id`,
  `object_category`, `object_type`, `object_attrs`, `result`, `result_id`,
  `status`, `user`, `src_user`, `dest`, `dest_name`
- Ticket convenience fields: `ticket_id`, `ticket_type`, `ticket_status`,
  `severity`
- Inventory model: `dest`, `dest_name`, `dest_host`, `dest_ip`, `ip`, `dns`,
  `nt_host`, `mac`, `owner`, `vendor_product`, `status`
- Identity lookup-friendly fields: `identity`, `user`, `user_id`,
  `user_email`, `user_bunit`, `user_category`, `user_priority`, `managed_by`

The optional Splunk app maps eventtypes to CIM tags:

- `snow:incident`, `snow:change_request`, and `snow:task_ci` get `tag=change`
- `snow:cmdb_ci` gets `tag=inventory`
- `snow:sys_user` gets `tag=identity` for ES identity-oriented demos

ServiceNow incidents are modeled as service-management ticket lifecycle changes
inside `Change.All_Changes`, which is the current CIM replacement for the older
Change Analysis model.

## Regenerate and validate the data

The committed data is generated by:

```bash
python3 scripts/generate_servicenow_demo_data.py
```

The generator uses a fixed seed, so regenerated files should be stable unless
the script changes. Validate the CIM-friendly fields with:

```bash
python3 scripts/validate_servicenow_cim.py
```

## Option 1: Load as Splunk lookups

Use the CSV files as lookups when you want fast demo joins with existing Splunk
Enterprise Security data.

Example searches:

```spl
| inputlookup servicenow_incidents.csv
| search u_security_incident=true cim_data_model=Change status=success
| stats count min(opened_at) as first_seen max(sys_updated_on) as last_updated by priority severity assignment_group u_splunk_correlation_search
```

```spl
| inputlookup servicenow_cmdb_ci.csv
| search cim_data_model=Inventory (u_pci_scope=true OR u_contains_pii=true)
| table dest dest_ip business_service environment support_group u_criticality u_edr_status owner vendor_product
```

```spl
| inputlookup servicenow_incidents.csv
| lookup servicenow_cmdb_ci.csv dest as dest OUTPUT dest_ip environment u_criticality u_pci_scope u_contains_pii
| search u_security_incident=true
| table number priority severity status dest dest_ip business_service u_splunk_notable_event_id u_mitre_tactic u_mitre_technique
```

## Option 2: Ingest JSONL as events

For a more realistic add-on style demo, ingest each JSONL file into a dedicated
index such as `snow` with ServiceNow-like sourcetypes. The included Splunk app
uses `KV_MODE=json` for search-time extraction. If you prefer index-time JSON
field extraction, configure `INDEXED_EXTRACTIONS=json` on the parsing tier and
set `KV_MODE=none` on the search head to avoid duplicate JSON fields.

Install or copy the optional config from:

```text
datasets/servicenow/splunk_app/TA-synthetic-servicenow/default
```

Then ingest the JSONL files:

```bash
$SPLUNK_HOME/bin/splunk add oneshot datasets/servicenow/jsonl/servicenow_incidents.jsonl \
  -index snow -sourcetype snow:incident -host synthetic-servicenow

$SPLUNK_HOME/bin/splunk add oneshot datasets/servicenow/jsonl/servicenow_change_requests.jsonl \
  -index snow -sourcetype snow:change_request -host synthetic-servicenow

$SPLUNK_HOME/bin/splunk add oneshot datasets/servicenow/jsonl/servicenow_cmdb_ci.jsonl \
  -index snow -sourcetype snow:cmdb_ci -host synthetic-servicenow

$SPLUNK_HOME/bin/splunk add oneshot datasets/servicenow/jsonl/servicenow_users.jsonl \
  -index snow -sourcetype snow:sys_user -host synthetic-servicenow

$SPLUNK_HOME/bin/splunk add oneshot datasets/servicenow/jsonl/servicenow_task_ci.jsonl \
  -index snow -sourcetype snow:task_ci -host synthetic-servicenow
```

Demo searches after ingestion:

```spl
index=snow tag=change sourcetype=snow:incident u_security_incident=true
| stats count as incident_count values(u_mitre_technique) as mitre_techniques by priority severity status assignment_group
```

```spl
index=snow sourcetype=snow:incident u_splunk_notable_event_id=*
| table _time ticket_id priority severity status dest business_service u_splunk_notable_event_id u_splunk_correlation_search
```

```spl
index=snow tag=change sourcetype=snow:change_request risk=High OR type=Emergency
| table _time ticket_id type ticket_status status risk impact business_service dest short_description
```

```spl
index=snow tag=inventory sourcetype=snow:cmdb_ci
| stats count by business_service environment u_criticality status
```

## Demo storyline ideas

- Show Splunk ES notable events creating or enriching ServiceNow incidents via
  `u_splunk_notable_event_id` and `u_splunk_correlation_search`.
- Use CMDB fields such as `u_pci_scope`, `u_contains_pii`, and `u_criticality`
  to explain risk-based prioritization.
- Join incidents to `task_ci` and `cmdb_ci` to show affected assets and business
  services during incident response.
- Compare high-risk change requests against new incidents to demonstrate change
  risk and post-change monitoring.
- Pivot on `tag=change` or `tag=inventory` to demonstrate CIM-normalized
  searches independent of raw ServiceNow field names.
